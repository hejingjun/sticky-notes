架构审查报告

桌面便签项目 — Sticky Notes (Tauri 2.x + Vue 3)

Strong

1. lib.rs 承担过多职责

src-tauri/src/lib.rs 495 行

问题

lib.rs 是一个浅层模块：接口（24 个 #[tauri::command]）几乎和实现一样复杂。它同时负责：窗口穿透/置顶、设置管理、WebDAV 同步（3 个完整命令）、窗口操作、自启动、托盘初始化、快捷键注册、Win32 桌面嵌入。理解任何一个功能都需要在 495 行中弹跳。

解决方案

将 lib.rs 拆分为多个深层模块，每个模块隐藏自己的实现细节：

  • window.rs — 窗口状态（穿透、置顶、透明度）
  • settings_cmd.rs — 设置相关命令（get/set theme, shortcut, webdav, opacity, autostart）
  • sync_cmd.rs — 同步命令（sync_notes, sync_push, sync_pull）
  • lib.rs 只保留 run() 和模块注册

收益

局部性：修改同步逻辑只需看 sync_cmd.rs，不需要在 495 行中搜索。杠杆：每个模块的接口更小，更容易理解和测试。

2. NoteCard.vue 职责过载

src/components/NoteCard.vue 364 行

问题

NoteCard 同时管理：主标题编辑、子任务编辑（独立状态）、颜色选择器、截止日期选择器、拖拽排序、置顶/完成/删除操作。每个功能都有自己的 ref 状态，相互交织。修改颜色选择器的逻辑需要理解整个组件的上下文。

解决方案

将 NoteCard 拆分为多个子组件，每个组件隐藏自己的状态：

  • NoteCard.vue — 容器，只负责布局和拖拽
  • ColorPicker.vue — 颜色选择器（showColors 状态内化）
  • DueDatePicker.vue — 截止日期选择器
  • SubtaskList.vue — 子任务列表（subEditingId 状态内化）

收益

局部性：修改颜色选择器只看 ColorPicker.vue。可测试性：每个子组件可以独立测试。NoteCard 从 364 行降到约 150 行。

前后对比

Before — 浅层

┌─────────────────────────┐ │ NoteCard.vue (364行) │ │ │ │ editing (主标题编辑) │ │ subEditingId (子任务) │ │ showColors (颜色) │ │ showDuePicker (日期) │ │ 拖拽逻辑 │ │ 6个 emit 事件 │ └─────────────────────────┘

After — 深层

┌──────────────────┐ │ NoteCard (~150行) │ ← 容器 + 拖拽 └────┬───┬───┬─────┘ │ │ │ ▼ ▼ ▼ Color Due Subtask Picker Date List (50行) (40行)(80行)

3. 同步逻辑缺少独立的接缝

src-tauri/src/lib.rs src-tauri/src/sync/mod.rs

问题

sync_notes / sync_push / sync_pull 三个命令直接嵌入 lib.rs，每个都有约 40 行的样板代码（获取 WebDAV 配置、构建 URL、读写 ETag）。这些重复模式违反了 DRY 原则，且同步逻辑无法独立测试。

解决方案

提取一个 SyncEngine 深层模块：

  • 接口：sync(), push(), pull()
  • 实现：WebDAV 配置获取、URL 构建、ETag 管理全部隐藏在内部
  • lib.rs 中的命令变成薄适配器，只做参数提取和错误转换

收益

杠杆：调用者只需调用 engine.sync()，不需要知道 ETag、URL 构建等细节。可测试性：SyncEngine 可以用 mock HTTP 客户端独立测试。

Worth exploring

4. useNotes.ts 排序逻辑可深化

src/composables/useNotes.ts 143 行

问题

useNotes 同时负责 CRUD 操作和排序逻辑。add() 和 reorder() 函数中有大量排序/重平衡代码（约占 60% 代码量），这些逻辑与数据操作耦合在一起。排序策略的变更（比如从 hex 改为其他编码）会影响整个 composable。

解决方案

排序逻辑已经部分提取到 utils/ordering.ts，但 add() 和 reorder() 中仍有内联的重平衡逻辑。可以进一步提取：

  • rebalanceNotes(notes, insertAt) — 封装重平衡逻辑
  • nextOrder(notes, parentId) — 封装"下一个排序值"计算
  • useNotes 只保留纯 CRUD + 调用排序工具

收益

局部性：排序策略变更只影响 ordering.ts。可测试性：排序逻辑可以独立单元测试，不需要 mock Tauri IPC。

Speculative

5. 前端事件监听缺乏统一模式

src/App.vue

问题

App.vue 中有 3 个手动管理的事件监听器（unlistenPen, unlistenTop, unlistenReload），每个都需要在 onUnmounted 中手动清理。这种模式容易遗漏，且随着功能增加会变得更混乱。

解决方案

创建 useTauriEvent composable，自动管理生命周期：

  • useTauriEvent('penetrate-changed', (v) => penetrating.value = v)
  • 自动注册、自动清理，无需手动管理 unlisten

收益

杠杆：一行代码替代三行（listen + 赋值 + unlisten）。减少内存泄漏风险。

最佳建议

首先处理 候选 1（lib.rs 拆分），理由：

  • lib.rs 是整个 Rust 后端的入口，495 行的浅层模块是最大的架构债务
  • 拆分后，后续的同步改进（候选 3）会自然落入 sync_cmd.rs
  • 这是纯重构，不改变任何外部行为，风险最低
  • 拆分后的模块结构会成为后续所有 Rust 代码的组织模板
